# Project Foundation: Vision and Scope

## 1. Vision

Project Foundation aims to establish a consistent, practical, and maintainable development ecosystem.

It provides shared standards, templates, automation, and documentation that help projects remain understandable and sustainable over time.

The vision is to make good development practices repeatable without sacrificing the independence and flexibility of individual projects.

## 2. Mission

Project Foundation exists to:

- Reduce duplicated development effort.
- Establish consistent project organization and documentation.
- Encourage modular and maintainable architecture.
- Improve testing and quality assurance.
- Promote secure development practices.
- Provide reusable automation and tooling.
- Make projects easier to maintain, troubleshoot, and hand off.
- Support future collaboration.

## 3. Identity

Project Foundation is maintained under the ShockingMilk identity.

ShockingMilk represents a shared creative and development identity rather than a legal business or corporate organization.

Projects developed under this identity remain independent and may have their own names, goals, contributors, and audiences.

Project Foundation provides shared resources without requiring every project to adopt identical branding or architecture.

## 4. Scope

Project Foundation covers several areas of development.

### 4.1 Development Standards

Shared guidance for:

- Architecture and modularity.
- Coding practices.
- Configuration management.
- Error handling and logging.
- Testing and quality assurance.
- Security and dependency management.
- Git workflows and collaboration.
- Release management.

### 4.2 Repository Standards and Templates

Reusable guidance and starting structures for:

- Repository organization.
- README and documentation.
- Contribution guidelines.
- Issue and pull request templates.
- Language-specific project structures.
- Framework-specific project structures.
- Development and deployment configuration.

### 4.3 Automation and CI/CD

Shared automation resources, including:

- GitHub Actions workflows.
- Automated testing.
- Code quality checks.
- Security scanning.
- Build validation.
- Release automation.
- Documentation validation.

Individual repositories retain their own workflow configuration and control over when shared automation is adopted.

### 4.4 Development Documentation

Practical documentation covering:

- Development environments.
- Repository setup.
- Testing procedures.
- Deployment practices.
- Troubleshooting.
- Maintenance and handoff.

### 4.5 Technology-Specific Guidance

Technology-specific standards and templates may be established for languages, frameworks, operating systems, hardware platforms, and deployment environments.

Examples include:

- Python.
- PowerShell.
- Django.
- Docker.
- Linux.
- Windows.
- Raspberry Pi and ARM-based systems.

These standards should extend the shared foundation rather than conflict with it unnecessarily.

## 5. Out of Scope

Project Foundation is not intended to:

- Become a centralized runtime dependency for individual projects.
- Require every project to use the same language or framework.
- Force identical repository structures on fundamentally different projects.
- Replace project-specific documentation.
- Mandate unnecessary tools or infrastructure.
- Introduce complexity solely for the sake of standardization.
- Function as a corporate entity or commercial organization.

Individual projects remain responsible for their own functionality, deployment, operational requirements, and project-specific decisions.

## 6. Standards Philosophy

Project Foundation distinguishes between two classifications.

### Required Standards

Practices expected across projects unless an exception is justified and documented.

Examples may include:

- Protecting credentials and sensitive configuration.
- Maintaining accurate documentation.
- Avoiding committed secrets.
- Providing appropriate testing for supported functionality.
- Keeping project configuration separate from implementation where practical.

### Recommended Standards

Preferred practices that may be adapted based on project needs.

Examples may include:

- Specific directory structures.
- Preferred testing frameworks.
- Particular logging conventions.
- Optional static analysis tools.
- Technology-specific architectural patterns.

The distinction allows shared expectations without imposing inappropriate technical requirements.

## 7. Independence and Reusability

Individual projects should remain independently maintainable.

Shared resources should be designed so projects can:

- Adopt them incrementally.
- Customize them when necessary.
- Pin reusable automation to known versions.
- Continue operating if Project Foundation is temporarily unavailable.
- Document deviations from shared standards.

Templates provide a starting point. Reusable workflows provide centrally maintained automation. Standards provide guidance.

These are related resources, but they serve different purposes.

## 8. Evolution and Governance

Project Foundation should evolve through practical experience.

New standards and shared resources should generally emerge from:

1. A demonstrated need.
2. A solution implemented in an actual project.
3. Testing and validation.
4. Evaluation for broader applicability.
5. Documentation and incorporation into Project Foundation.

Standards should be periodically reviewed as technologies, security practices, and project requirements change.

Established guidance should not be changed casually when doing so could disrupt consuming projects.

## 9. Initial Development Priorities

The initial development effort will follow the established project rollout:

1. One-Click IT Toolkit
2. AstroLab
3. Meetinghouse Broadcast
4. Meetinghouse Technology
5. AD Cleanup
6. Cluster

Each project will help validate and improve the shared standards, templates, and automation.

The order may be adjusted if a significant technical or security need warrants it.

## 10. Long-Term Goal

The long-term goal is a development ecosystem in which projects can begin with a reliable foundation, follow understandable conventions, and benefit from improvements made elsewhere.

Project Foundation should become a useful resource that makes projects easier to build, maintain, and share.

**Build consistently. Develop confidently. Improve continuously.**
